# TDD 范围判定

按行为风险判定整个任务，不按文件扩展名或工作量判定。

## TDD required

以下变更必须先 Red，再 Green，最后按需 Refactor：

- 功能开发、bug 修复或可执行重构；
- API、数据、状态、校验、序列化、查询或缓存；
- 权限、安全、迁移、构建和运行配置分支；
- UI 布局、样式、渲染、交互、表单、导航或可访问性行为；
- 会改变解析、生成输出或公共契约的变更；
- 文案与行为混合的任务；
- 分类证据不足或不确定的任务。

测试、fixture、mock 和 test helper 为生产行为服务时，整个生产任务仍按 TDD 执行。不得改写正确测试来迎合错误实现。

## TDD not required

只有证明确实不改变运行行为时才可跳过 TDD：

- 纯文案或翻译值；
- 注释或说明性文档；
- 纯格式且语义 diff 为空；
- 没有运行消费者的静态 metadata；
- 契约和尺寸不变的静态资源替换。

仍需执行适用的 diff、schema、链接、拼写、渲染、snapshot、parser、build 或文件属性验证。

如果翻译 key、文档示例、metadata、资源尺寸或格式会影响运行、布局、解析、生成输出或公共契约，则改为 `TDD required`。

测试基础设施不可用是需要解决或报告的 blocker，不是模拟 TDD 或事后补测试的理由。
